1.1 事件循环忙等 (Busy-wait spin loop)
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xthread.cpp:155-160
  严重度: 高危 🔴
  类型: 性能

  代码:
    while (!is_exit_)
    {
        event_base_loop(base_, EVLOOP_NONBLOCK);
        this_thread::sleep_for(1ms);
    }

  问题: 每个线程每1ms轮询一次 libevent，即使完全空闲也持续唤醒 CPU。
        如果有 N 个线程，就是 N 个 CPU 核心每秒被唤醒 1000 次。

  解决方案: 改用 event_base_dispatch(base_)（阻塞模式），或
            event_base_loop(base_, 0)（阻塞直到有事件），
            退出时用 event_base_loopbreak()。空闲时 CPU 占用接近零。

1.2 Base64Decode 内存泄漏 (BIO_free_all 释放错误对象)
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xtools.cpp:149
  严重度: 高危 🔴
  类型: 内存泄漏

  代码:
    BIO_free_all(mem_bio);  // 错误！应释放 b64_bio

  问题: Base64Decode 中 BIO_free_all(mem_bio) 只释放了内存 BIO，
        漏掉了 b64_bio（Base64 过滤器 BIO）。而 Base64Encode 中
        正确使用了 BIO_free_all(b64_bio)（第126行）。
        每次调用 Base64Decode 泄漏一个 BIO_f_base64 对象。

  解决方案: 将第149行 BIO_free_all(mem_bio) 改为 BIO_free_all(b64_bio)，
            与 Base64Encode 保持一致。

──────────────────────────────────────────────────────────────────────────────

1.3 XRegisterClient 中 strcpy 缓冲区溢出
──────────────────────────────────────────────────────────────────────────────
  文件: register_client/xregister_client.cpp:293-295
       register_client/xregister_client.h:72-74
  严重度: 高危 🔴
  类型: 缓冲区溢出/安全

  代码:
    char service_name_[32] = {0};
    char service_ip_[16] = {0};
    ...
    strcpy(service_name_, service_name);
    if (ip) strcpy(service_ip_, ip);

  问题: 无长度检查的 strcpy 将调用方提供的字符串复制到固定大小
        的栈缓冲中。服务名超过31字节或IP超过15字节会导致栈溢出。

  解决方案: 使用 strncpy 并确保 null 终止，或改用 std::string 成员变量。

──────────────────────────────────────────────────────────────────────────────

1.4 互斥锁销毁时其他线程可能仍在引用 (Use-after-free)
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xcom_task.cpp:81-89, 222-253
  严重度: 高危 🔴
  类型: 线程安全/Use-after-free

  问题: XComTask::Close() 通过 XMutex 锁定 mux_ 后，若 auto_delete_
        为 true，会调用 delete this → ~XComTask() → delete mux_。
        此时其他线程（如 Write()、Read()、BufferSize()）可能仍持有
        指向 mux_ 的指针，造成 use-after-free。

  解决方案: 在 delete this 前确保没有其他线程再访问该对象。
            可以在 Close() 中先标记对象为"已关闭"，再由事件循环
            延迟删除，或使用 shared_ptr/weak_ptr 管理生命周期。

──────────────────────────────────────────────────────────────────────────────

1.5 全局回调映射表无同步 (Global callback map data race)
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xmsg_event.cpp:14-24, 30
  严重度: 高危 🔴
  类型: 线程安全/Data race

  代码:
    static map<MsgType, XMsgEvent::MsgCBFunc> msg_callback;
    ...
    void XMsgEvent::RegCB(...) { msg_callback[type] = func; }  // 写
    void XMsgEvent::ReadCB(...) { ... msg_callback.find(...) ... }  // 读

  问题: msg_callback 是模块级静态 map，RegCB（写）和 ReadCB（读）
        都在多线程环境下调用，但没有互斥锁保护，存在 data race。

  解决方案: 添加 std::mutex 或 std::shared_mutex 保护 msg_callback 的读写。

1.6 非标准 AES 零填充 (Non-standard zero padding)
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xtools.cpp:787-790, 804-839
  严重度: 高危 🔴
  类型: 数据完整性

  问题: AES 加密使用零填充（unsigned char data[16] = {0}），不是标准
        PKCS#7 填充方案。如果明文末尾含有零字节，解码器无法区分
        是填充还是数据，导致静默数据损坏。解密函数没有去除任何填充。

  解决方案: 改用 PKCS#7 标准填充，或使用 EVP 层 API（EVP_CIPHER_CTX）
            替代已弃用的低层 AES_encrypt/AES_decrypt API。

1.7 死代码分支 (Dead duplicate code block)
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xtools.cpp:213-216

  类型: 代码质量/复制粘贴错误

  问题: XGetIconFilename 中扩展名为 "doc/docx/wps" 的分支在 193-196

1.8 WSAStartup 竞态条件 (Race condition on WSAStartup)
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xtools.cpp:649-659
  严重度: 高危 🔴
  类型: 线程安全

  代码:
    static bool is_init = false;
    if (!is_init) {          // 无锁检查
        WSAStartup(...);
        is_init = true;
    }

  问题: 静态 is_init 标志的检查和设置没有互斥锁保护。多线程同时
        调用 XGetHostByName 时可能重复执行 WSAStartup，或者
        一个线程尚未完成初始化时另一个线程就已经跳过了。

  解决方案: 使用 static std::once_flag + std::call_once，
            或 static std::mutex 保护初始化代码。

1.9 gethostbyname 非线程安全
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xtools.cpp:662
  严重度: 高危 🔴
  类型: 线程安全

  问题: gethostbyname 返回指向内部静态数据的指针，且多数平台上

  解决方案: 改用 getaddrinfo（可重入且协议无关），替换 gethostbyname +
            inet_ntoa 组合。

2.1 strncpy 不保证 null 终止
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xcom_task.cpp:94, 99, 190, 195
  严重度: 中危 🟡
  类型: 缓冲区安全

  问题: 四处 strncpy 调用中，set_local_ip 和 set_server_ip 缺少
        null 指针保护（与 set_error 和 set_client_ip 不一致）。
        且 strncpy 在源串 >= 目标大小时不写 null 终止符。
        client_ip_[16] 和 server_ip_[16] 若被 15+ 字符的 IP 填充，
        后续字符串操作会越界读取。

  解决方案: 添加 null 检查，并在 strncpy 后手动写 null 终止符：
            strncpy(dest, src, sizeof(dest) - 1);
            dest[sizeof(dest) - 1] = '\0';

──────────────────────────────────────────────────────────────────────────────

2.2 GetServcies 在持有锁期间睡眠
──────────────────────────────────────────────────────────────────────────────
  文件: register_client/xregister_client.cpp:105-131
  严重度: 中危 🟡
  类型: 性能/线程安全

  问题: 轮询循环中 XMutex mutex(&service_map_mutex) 在每次迭代
        开始时获取锁，然后在持有锁的情况下 sleep 10-100ms。
        这阻塞了其他所有线程（如 GetServiceRes、GetAllService）
        访问 service_map 的能力。

  解决方案: 缩小锁范围，在 sleep 前释放锁，sleep 后重新获取。

──────────────────────────────────────────────────────────────────────────────

2.3 无边界检查的 sprintf
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xtools.cpp:534, 552
  严重度: 中危 🟡
  类型: 缓冲区溢出

  问题: GetDirData 的 Windows 和 POSIX 路径都使用 sprintf(buf, ...)
        向固定 1024 字节 buf 写入。某些文件系统上路径可能超过
        1024 字节（Linux 单个文件名 255 字节，完整路径可以更长）。

  解决方案: 使用 snprintf 替代 sprintf，指定缓冲区大小。

──────────────────────────────────────────────────────────────────────────────

2.4 日志队列无上限 (Unbounded log queue)
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xlog_client.cpp:61, 75-77
  严重度: 中危 🟡
  类型: 内存/OOM 风险

  代码:
    std::list<xmsg::XAddLogReq> logs_;
    ...
    logs_.push_back(tmp);  // 生产者
    // 消费者: TimerCB 每 100ms 处理

  问题: logs_ 是 std::list，没有最大大小限制、没有丢弃策略、
        没有背压机制。当 DEBUG 级别日志大量产生时，如果生产
        速度超过 100ms 定时器的消费速度，队列内存无限增长。

  解决方案: 添加高水位标记（如最大 10000 条），超限时丢弃最旧
            的日志或丢弃新日志。或使用环形缓冲区。

──────────────────────────────────────────────────────────────────────────────

2.5 每次注册响应都写磁盘缓存文件
──────────────────────────────────────────────────────────────────────────────
  文件: register_client/xregister_client.cpp:213-228
  严重度: 中危 🟡
  类型: 性能/磁盘 I/O

  问题: GetServiceRes 回调中，每次收到注册服务器的响应都执行：
        - 打开文件
        - 完整 protobuf 序列化整个服务列表
        - write 系统调用
        - 关闭文件
        开发者在第213行注释 "disk cache refresh, should consider
        refresh frequency later" 确认已意识到这个问题。

  解决方案: 限制写频率（如最多每 N 秒写一次），或延迟到后台
            定时器执行。

2.6 GetAllService 每次深拷贝整个服务列表
──────────────────────────────────────────────────────────────────────────────
  文件: register_client/xregister_client.cpp:152
  严重度: 中危 🟡
  类型: 性能

  代码: client_map->CopyFrom(*service_map);

  问题: GetAllService() 每次深拷贝整个 XServiceMap protobuf 对象。

  解决方案: 返回 const 引用（调用方确保不修改），或使用引用计数

2.7 轮询循环中重复发送网络请求
──────────────────────────────────────────────────────────────────────────────
  文件: register_client/xregister_client.cpp:102-134
  严重度: 中危 🟡
  类型: 性能/网络

  问题: 当服务未在缓存中找到时，每隔 100ms 重新发送一次
        GetServiceReq 网络请求，产生不必要的网络流量。

  解决方案: 只需发送一次请求，用超时等待替代重复请求。

2.8 XMsgEvent::ReadCB 中 while(1) 阻塞事件循环
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xmsg_event.cpp:44-87
  严重度: 中危 🟡
  类型: 性能/事件循环

  问题: ReadCB 在 libevent 回调中同步处理所有待处理消息的 while(1)
        循环。消息洪泛会饿死同一线程上的：
        - 其他连接的处理
        - 定时器事件（心跳、自动重连）
        - 写完成回调

  解决方案: 每次回调只处理一条消息，或设置最大处理数量后
            让出事件循环。

2.9 SendMsg 中 msg 空指针解引用
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xmsg_event.cpp:227
  严重度: 中危 🟡
  类型: 空指针

  代码:
    if (!head) return false;  // 只检查 head，不检查 msg
    head->set_msg_size(msg->size);  // msg 可能为 NULL！

2.10 EventCB 中 Event flags 重叠时的 Use-after-free

  文件: xplatform/xcom_task.cpp:322-358
  严重度: 中危 🟡

  问题: for(;;) 一次处理所有累积日志。如果积压了数千条，
        会长时间阻塞事件循环，导致 socket 超时。

  解决方案: 每次 TimerCB 最多处理 N 条（如 100 条），
            剩余的等下一次定时器触发。

3.11 线程分发计数器非线程安全
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xthread_pool.cpp:53-54
  严重度: 低危 🟢
  类型: 线程安全

  代码:
    int tid = (last_thread_ + 1) % thread_count_;
    last_thread_ = tid;

  问题: 多个监听线程同时分发任务时，last_thread_ 的读写无保护，
        可能导致分发到重复或错误的线程。

  解决方案: 使用 std::atomic<int> 替代 int，或加锁。

3.12 全局 all_threads 跨线程池共享
──────────────────────────────────────────────────────────────────────────────
  文件: xplatform/xthread_pool.cpp:22-23
  严重度: 低危 🟢
  类型: 设计问题

  问题: static vector<XThread*> all_threads 是模块级全局变量。
        XService 创建两个线程池（监听+客户端），调用
        ExitAllThread() 会误杀其他池的线程。

  解决方案: 每个线程池实例管理自己的线程列表，或使用线程组 ID。

6.1 xthread.cpp — 事件循环忙等 → EVLOOP_ONCE + event_base_loopbreak
============================================================================

Before (CPU 忙等):

  {
      event_base_loop(base_, EVLOOP_NONBLOCK);
      this_thread::sleep_for(1ms);
  }

After (阻塞等待，空闲时 CPU ≈ 0%):
  while (!is_exit_)
  {
      event_base_loop(base_, EVLOOP_ONCE);
  }
  event_base_free(base_);

配套改动: XThread::Exit() 改为 virtual，CXThread 覆盖:
  virtual void Exit() override
  {
      XThread::Exit();
      if (base_)
          event_base_loopbreak(base_);
  }
